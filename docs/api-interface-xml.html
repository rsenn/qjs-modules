#Plan: the xml interface against Browser, Bun, Node and Deno (2026-10-17)

> Status 2026-10-18 (implemented). The event model is in: every class is a source or sink over JsonEvent / XmlEvent, pump()/connect()/tee/JsonBuilder/XmlBuilder exist, parse() and XMLNodeParser are removed (next() and the iterator replace them), xml.write() is xwalk pumped into an XmlWriter (XW_PRETTY, indent 2), quickjs-json.c is 933 and quickjs-xml.c 967 lines. > Running state and what is left: event-model-state.md. Text below that describes parse(), XMLNodeParser, > eventName/eventValue, PARSE_*, xtreewrite or xlayout is the plan or the history, those are gone.

Goal: the JS surface of import ... from 'xml' follows the standards in this order: WHATWG > Browser > Bun > Node > Deno (CLAUDE.md), keeps the tagName/attributes/children tree that lib/dom.js is built on, and adds no custom public API. Findings are in api-compare-xml.md, the code split in api-implement-xml.md; the step list that orders all three is TODO.md Tier 20. Sections 4 to 10 below are the reference: the C contracts between the pieces and the JS contract of each class.

Layering (plan 2026-10-18, api-event-model.md). The xml native module exports engines only: pull and push parsers, builder (tree and flat), walker, writer, serializer, sink adapters, all sources or sinks of XmlEvent. read, write, DOMParser, XMLSerializer, XML.parse, XML.stringify and the XMLNodeParser shape are thin compositions of those engines in JS (lib/xml.js, lib/dom.js, lib/bun.js): "Lives in" below. A flat parse is XMLParser({flat: true}) pumped into a flat XmlBuilder (a list of element objects, an end is a {tagName: '/x'} entry), entirely in C. Sections 4 to 8 describe the contracts as they are; the event model marks what changes (pull parser writes an XmlEvent, push parser calls an XmlEvent handler, walker is a pull source that speaks XmlEvent, serializer is demand-driven).

#4. Reference: the event protocol: what exists and what is missing

JSON and XML each have one vocabulary (JsonEventType, XmlEventType) shared by reader, builder, walker and writer. For XML it is include/xml/xevent.h; the parsers differ only in how they hand it out:

Planned (Tier 20 phase 1): one xe_type_t order shared by both parsers, xwrite and xbuilder; one string type; one callback (xe_callback(type, name, value, user_data)); an XMLWriteInterface of function pointers like JsonWriteInterface, returned by xwrite_interface(wr); the typed markup events, so xbuilder can map them back to the magic names for read() compatibility. Until then the two enums stay and each adapter translates.

Done since: XmlEventType, XmlEvent, XmlEventSink (xevent.h), xwrite_sink, xbuild_sink, the pumps. Plan 2026-10-18 (api-event-model.md 3.2, 4): the pull parser returns XmlPull (XML_PULL_END | AGAIN | EVENT | FAIL) and fills an XmlEvent (xml_next(p, &ev)), which replaces the event_name / event_value / event_has_value fields and the XML_PARSE_* statuses (an XE_ERROR is an event, then XML_PULL_END); the push parser calls an XmlEventHandler with the same XmlEvent, which replaces xr_callback / xr_str_t; xread_pump / xml_pump are then the 3-line loop.

#xr_read / xr_finish (push, xread.h)

typedef void (*xr_callback)(XmlEventType type, const xr_str_t* name, const xr_str_t* value, void* user_data);

Chunks may end anywhere; name and value are valid inside the callback; a value-less attribute has value == NULL; xr_finish reports XE_ERROR when elements are still open. No tolerant mode, no implied ends, no flat mode, no locations.

#7. Walking: WalkInterface and XwalkIterator (walk.h, xwalk.h)

xwalk reports a tree of elements through the same WalkInterface as jwalk, configured by two WalkHooks:

Tree partWalked as
an element objectexactly the keys tagName, attributes, children, in that order, each read with a plain property get (prototype getters work), skipped when undefined
attributesan object, by its own enumerable keys; its values are values, never containers
childrenan array, by index; an object item is an element, anything else a value; a nested array is a value
a root arraya list of elements and texts
every other propertynever read (parentNode, ownerDocument, line cannot cause a cycle)
XwalkIterator it;  xwalk_init(&it, ctx, tree, iface, NULL /* XwalkShape: tag, attributes, children */);
while((r = xwalk_next(&it, ctx)) > 0) {}   xwalk_close(&it, ctx);

Planned (step 4d): an adapter that turns these walk events into xwrite calls (the table is in TODO.md Tier 20 phase 4), reading the children count at array_start and using one event of lookahead for the flat-list rule (self-closing iff the next entry is the element's own /x marker).

Plan 2026-10-18 (api-event-model.md 5): that adapter is xwalk_event(&src, &ev), a pull source of XmlEvent, the same translation (xtreewrite.c today) living in the walker. xtreewrite shrinks to a pump into xwrite, XMLTreeSerializer is the walker behind the demand-driven serializer, and js_walk_* for XML is replaced by the sink methods of js_xmlsink_define.

#11. Errors and locations: the contract

The exception classes, the loc object, and the position rules are those of api-interface-json.md section 11 (SyntaxError with own non-enumerable loc, length, code; TypeError for bad arguments; callbacks' exceptions unchanged; AggregateError for collected errors). XML specifics:

#11.1 Where each failure appears

Mode / APIFailureResult
xml.read(), XML.parse() strictmalformed documentthrows SyntaxError (loc, length, code)
xml.read() lenient (default today)a repair (stray end tag, implied end, void element, unterminated tag at EOF)no exception; optional onParseError(err) with the same shape
XMLParser, XMLNodeParsermismatched end tag with tolerant offparse() returns PARSE_ERROR; parser.error holds the SyntaxError; .location is the position of the next token as now
XMLPushParsermismatch while writing; truncated input on close()SyntaxError with loc at the point; onParseError in lenient use

DOMParser.parseFromString(s, 'text/xml')malformed documentno exception; the result's document element is <parsererror> carrying the message and line/column text (Browser)
HTML mode of the DOMany inputnever an error; repairs go to onParseError only

#11.2 Codes (XML)

Strict: mismatched-end-tag, unexpected-eof-in-tag, unexpected-eof-in-element, duplicate-attribute, unquoted-attribute-value, missing-attribute-value, undefined-entity, invalid-character-reference, multiple-roots, text-outside-root, missing-root, invalid-character, unterminated-comment, unterminated-cdata, bad-xml-declaration, invalid-name. Lenient repairs reuse the HTML spec's names where one exists (end-tag-without-matching-open-element, eof-in-tag, duplicate-attribute, unexpected-null-character). loc is the < of the tag or the first character of the offending token; for a mismatched end tag it is the start of the end tag (what xml.read() already prints), with length covering it.
