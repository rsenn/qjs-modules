#Plan: the json interface against Browser, Bun, Node and Deno (2026-10-17)

> Status 2026-10-18 (implemented). The event model is in: every class is a source or sink over JsonEvent / XmlEvent, pump()/connect()/tee/JsonBuilder/XmlBuilder exist, parse() and XMLNodeParser are removed (next() and the iterator replace them), xml.write() is xwalk pumped into an XmlWriter (XW_PRETTY, indent 2), quickjs-json.c is 933 and quickjs-xml.c 967 lines (2026-10-18: json.c is gone, JsonParser is a queue over jread; the push parser, the serializer and the pump moved into src/json/). > Running state and what is left: event-model-state.md. Text below that describes parse(), XMLNodeParser, > eventName/eventValue, PARSE_*, xtreewrite or xlayout is the plan or the history, those are gone.

Goal: the JS surface of import ... from 'json' follows the standards in this order: WHATWG > Browser > Bun > Node > Deno (CLAUDE.md), adds no custom public API, and keeps the classes nobody else offers as engines under that surface. Findings are in api-compare-json.md, the code split in api-implement-json.md; the step list that orders all three is TODO.md Tier 18. Sections 4 to 10 below are the reference: the C contracts between the pieces and the JS contract of each class.

Layering (plan 2026-10-18, api-event-model.md). The json native module exports engines only: pull and push parsers, builder, walker, writer, serializer, sink adapters. Every API of the table below that is a dialect or a runtime shape (JSONL, JSON5, JSONC, read, write, Blob.prototype.json(), the @std/json streams) is a thin composition of those engines in JS under lib/ (lib/jsonl.js, lib/json5.js, lib/jsonc.js, lib/bun.js, lib/jsonStreams.js); the "Action" column says what the API does, the new column "Lives in" says where. Sections 5 to 8 describe the C contracts as they are; where the event model changes them (the pull parser writes a JsonEvent, the push parser calls a JsonEvent handler, the walker is a pull source, the serializer is demand-driven) the change is marked "plan 2026-10-18" and specified in api-event-model.md 3 to 5.

#2. Decisions

#DecisionReason
D1no JSONL.stringify, no JSONC.stringifyno runtime has them
D2JSON5.parse / JSONC.parse take one argument, no reviver; trailing data is a SyntaxErrorBun's length and behaviour
D3everything that parses for Bun parity builds ordinary-prototype objects; null-prototype stays only inside internal readersJSON.parse results have Object.prototype
D4error class is the contract (SyntaxError, TypeError), message texts follow the engineBun's texts are not stable either
D5no Node streams (stream-json's API is not copied)CLAUDE.md; the WHATWG forms of @std/json are the target
D6read's string-escape defect is fixed before it is deprecatedit is wrong today and callers exist (plot-cv/yt-playlist.js, plot-cv/clang-ast.js)
D7every parser throws SyntaxError with an own loc (a Location), length and code; section 11no runtime offers a correct structured position (api-compare-json.md 7); one property name, loc, on the standard class
D8TypeError for bad argument types (not ReferenceError); InternalError never for inputread(5) throws ReferenceError, read('{') an InternalError today
D9decided 2026-10-18: no dialect or runtime API is C. JSONL, JSON5, JSONC, read, write are compositions of engine classes in lib/one set of engines serves Browser, Bun, Node and Deno shapes; the engines stay replaceable by a pure-JS port
D10decided 2026-10-18: every engine class is a source or a sink, pull or push; a source reaches a sink in C through pump(sink) / connect(sink)api-event-model.md 1 and 2
D11the dialect is a name ('json', 'jsonc', 'json5', 'jsonl') given to the parser; the JR_* flags behind it are an implementation detailone entry point per role, no parseJson5 family

The event-model steps P1 to P10 (api-event-model.md 10, TODO.md "Event model v2") run alongside: P1 to P8 change the engines (json_next(p, &ev), push handler, walker as source, demand-driven serializer, handshake, builder queue, parser options), P9 moves JSONL, JSON5, JSONC, read, write into lib/. Steps 3 and 5 above are then done in the glue; step 2 (jread strict and dialects) is P8's input.

#4. Reference: the event protocol

One vocabulary connects reader, builder and writer: JsonEventType (include/json/jevent.h), in this order.

JsonEventTypeCarriesjwrite calljbuild callWalk event
JSON_EVENT_ERRORmessagejwrite_error(str, len)nonenone (a walk throws)
JSON_EVENT_NULLjwrite_nulljbuild_valuevalue()
JSON_EVENT_TRUE, JSON_EVENT_FALSEjwrite_true, jwrite_falsejbuild_valuevalue()
JSON_EVENT_NUMBERtextjwrite_number(str, len)jbuild_value (scan_double)value()
JSON_EVENT_STRINGdecoded UTF-8jwrite_string(str, len)jbuild_valuevalue()
JSON_EVENT_ARRAY_START, _endjwrite_array_start, _endjbuild_push, jbuild_poparray_start, array_end
JSON_EVENT_OBJECT_START, _endjwrite_object_start, _endjbuild_push, jbuild_popobject_start, object_end
JSON_EVENT_KEYdecoded UTF-8jwrite_key(str, len)jbuild_keykey()

Strings and keys arrive decoded; jwrite re-escapes them. Numbers travel as text so 1e400 and 12345678901234567890 survive a parse-write chain untouched.

#5. Reading

#jr_read / jr_finish (push, jread.h)

typedef void (*jr_callback)(JsonEventType type, const jr_str_t* data, void* user_data);
void jr_state_init(jr_state_t*);   void jr_state_free(jr_state_t*);
void jr_read(jr_callback cb, const char* chunk, size_t len, void* user_data, jr_state_t*);
void jr_finish(jr_callback cb, void* user_data, jr_state_t*);
Contract
chunkinga chunk may end anywhere (mid-string, mid-escape, mid-number, mid-literal); the state resumes
datavalid only inside the callback; copied from an internal accumulator
errorsJSON_EVENT_ERROR once per bad span, then resync at the next comma or closing bracket; state->just_erred says whether this call hit one, state->error is sticky
numbersa bare number has no terminator, so only jr_finish() closes a trailing one
enginenone; Vector for the nesting stack (allocator set by jr_state_init)
plannedstrict mode (no comments, no resync, no trailing commas) and JSON5 / JSONC dialect flags

#json_parse (pull, json.h)

BOOL json_init(JsonParser*, Reader, const char* filename, JSContext*);
int  json_parse(JsonParser*);   /* a JsonEventType, JSON_NEED_DATA, or JSON_ERROR */
Contract
resultJSON_EVENT_* (JsonEventType of json/jevent.h, comment included), or JSON_NEED_DATA (reader dry, call again), or JSON_ERROR (json->error; jpump turns it into JSON_EVENT_ERROR)
payloadthe current token text in json->token (a DynBuf), valid until the next call
positionjson->loc (Location), json->pos
commentsskipped, or JSON_EVENT_COMMENT when json->comments is set
engineJSContext only to allocate the Location

Plan 2026-10-18 (api-event-model.md 3.1, 4): json_next() is added next to json_parse() (which stays the low-level step until the binding is off it): JsonPull json_next(JsonParser*, JsonEvent* ev), with JsonPull = JSON_PULL_END | AGAIN | EVENT | FAIL; the event carries type, token text and the start SourcePos, and an error is an event (JSON_EVENT_ERROR), so JSON_NEED_DATA, JSON_NONE and JSON_ERROR disappear as return values. The push side becomes jr_feed(state, chunk, len, JsonEventHandler*, user) with the same JsonEvent, and jr_callback / jr_str_t go. After that the pull and push parsers use one event type, one text rule and one position rule, and jread_pump / json_pump are the 3-line loop.

#7. Walking: WalkInterface and WalkHooks (walk.h, jwalk.h)

typedef struct {
  void* opaque;
  ssize_t (*key)(void*, JSContext*, JSValueConst);
  ssize_t (*object_start)(void*, JSContext*);   ssize_t (*array_start)(void*, JSContext*);
  ssize_t (*object_end)(void*, JSContext*);     ssize_t (*array_end)(void*, JSContext*);
  ssize_t (*value)(void*, JSContext*, JSValueConst);
  ssize_t (*raw)(void*, JSContext*, JSValueConst);   /* optional: JSON.rawJSON() object */
} WalkInterface;

Each callback returns bytes written (>= 0) or -1 with an exception pending. walk_next() returns the event (WALK_EVENT_KEY ... WALK_EVENT_VALUE, > 0), 0 when done, -1 on error. WalkHooks:

HookQuestion it answersjwalk answer
prepare(holder, key, &val)value, container, raw, or omit?toJSON, replacer, boxed primitives, NaN to null, bigint throws, undefined/function/symbol omitted
keys(top, array)which keys of an object, in which order?the array replacer's allow list
circularmessage of the circular TypeError"Converting circular structure to JSON"

JwalkIterator embeds a WalkIterator and must not move once initialised (the hooks point back at it). js_walk_register / js_walk_define / js_walk_wrap expose a WalkInterface to JS (key, objectStart, arrayStart, objectEnd, arrayEnd, value), which is how a producer drives a JsonWriter without knowing its class.

Plan 2026-10-18 (api-event-model.md 5): jwalk becomes a pull source of JsonEvent (jwalk_event(&src, &ev); strings as CESU-8, numbers as their JSON.stringify text, NaN / Infinity as null, JSON.rawJSON through JsonEventSink.raw). WalkInterface stays as the engine-side capture inside the iterator, not something a writer implements; js_walk_* is replaced by the sink methods of js_jsonsink_define. A walker pumped into a JsonWriter is write() / JSON5.stringify; a walker behind a JsonSerializer is the demand-driven stringifier.

#8. Writing: JsonWriter and JsonWriteInterface (jwrite.h)

Every call returns the bytes written (>= 0) or -JWRITE_E_*; jwrite_error_message(code) gives the text.

CodeMeaning
JWRITE_E_WRITE, _NOMEMthe Writer refused bytes; the frame stack could not grow
_EXPECTED_KEY, _KEY_AT_ROOT, _KEY_IN_ARRAY, _EXPECTED_VALUE, _PENDING_KEYkey and value out of order
_UNMATCHED_OBJECT/ARRAY, _NOT_ARRAY, _NOT_OBJECTend event without or against the open container
_SOURCEjwrite_error() passed a reader error through
_NUMBERnumber text empty or with a byte no number has

JsonWriteOptions: indent (spaces, 0..), indent_str + indent_len (a string per level), minify, and the JSON5 trio bare_keys, single_quotes, hex_numbers. JsonWriteInterface is the same events as function pointers (true_/false_ because true/false are macros), with opaque first.

C helpers that cross into JS state their error contract in one of three fixed forms (CLAUDE.md): "returns 0, or -1 with an exception pending", "returns NULL with errno set", "never throws".

loc, length and code are own, writable, configurable and non-enumerable (like cause), so JSON.stringify(err) and Object.keys(err) stay as for any error.

#11.2 loc

A Location (module location): file, line, column, charOffset, byteOffset; String(loc) is file:line:column.

RuleValueWhy
which positionthe start of the offending token (length characters long, 0 at end of input)JSON.parse tools, json5 and jsonc-parser agree; JsonParser reports the position after the token today (2:8 for 2:7)
baseline and column 1-based, offsets 0-basedjson5, xmldom, parse5
line breaks\n, \r\n as one, a lone \rHTML and XML normalise them; Location counts \n only today
column unitopen decision: code points (today) or UTF-16 unitsJS tooling and JSONL.parseChunk().read count UTF-16 units; recommendation: UTF-16 for column and charOffset, byteOffset stays UTF-8
filethe filename argument; empty for text without a name (Blob.json())
independencea clone made at throw time, not the live parser Locationthe parser goes on mutating its own

Aliases (lineNumber, columnNumber, fileName) are not added to the error; Location already accepts them on input.

#11.3 Codes (JSON)

unexpected-token, unexpected-eof, unexpected-comment, trailing-comma, trailing-data, invalid-escape, invalid-number, invalid-unicode, unterminated-string, control-character, unquoted-key, duplicate-key (strict dialects only), nesting-too-deep (only when a maxDepth is set; the default is unlimited, as Bun's 100000 levels). The dialect (json, json5, jsonc) decides which of them can occur.

#11.4 Location tracking in the parsers

ParserPosition todayTarget
JsonParserlive .location, end of token.location at the start of the token just returned; errors carry it as loc

read, JSON5/JSONC.parse, Blob.json()nonejread strict mode reports loc
JSONL.parse/parseChunkread (units)error.loc relative to the whole input, with line counting the newline-separated values
per valuenoneoptional onValue info carries offset (planned with onValue)

C side: a small engine-free SourcePos {offset, line, column} with srcpos_advance(pos, bytes, len) shared by jread, json, xread, xml; Location is filled from it at throw time (api-implement-json.md section 5).
