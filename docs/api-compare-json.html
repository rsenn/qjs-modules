#JSON: our API against Browser, Bun, Node, Deno and JS packages

What json (quickjs-json.c, lib/jsonStreams.js) offers, set next to what the other runtimes and the widely used npm/jsr packages offer. Priority when they disagree is the one of CLAUDE.md: WHATWG > Browser > Bun > Node > Deno. Companion documents: api-implement-json.md (how the code is split), api-interface-json.md (the interfaces between the pieces), native/json.md (the module reference).

Method: every row marked "probed" was run on node 22.23.3, bun 1.4.2, deno 2.9.7 and the qjsm of this tree (2026-10-17); packages were installed and run (@streamparser/json 0.0.26, json5 2.2.3, jsonc-parser 3.3.1, jsonparse 1.3.1, lossless-json 4.3.2, stream-json 3.7.0, jsr:@std/json). Anything not probed says so.

Nothing in the platform parses incrementally, reports tokens, or writes JSON incrementally. All of that is library territory, which is where our non-standard classes live.

#2. JSON.parse conformance (probed, 27 inputs)

The four runtimes agree on every input: BOM, trailing commas, comments, NaN, single quotes, bare keys, 1 2, empty and whitespace-only text, 01, 1., .5, +1, 0x10, a raw tab in a string are all SyntaxError; "__proto__" is an own property; duplicate keys keep the last; "\ud800" is kept; 1e400 is null after JSON.stringify; -0 stays -0.

One difference: nesting 100000 deep ('['.repeat(1e5)) parses on node, bun and deno and is a SyntaxError ("stack overflow") on qjsm, because JS_ParseJSON recurses. 10000 deep is fine everywhere. This is why Blob.prototype.json() is not yet 100 % Bun compatible.

#6. Findings and what they decide

  1. read() and write() duplicate JSON.parse/JSON.stringify; read is wrong in four ways (section 3). Plan: deprecate both after the Bun namespaces exist, migrate plot-cv/yt-playlist.js and plot-cv/clang-ast.js, then remove (Tier 18 step 5). Until then read should decode escapes (BUGS).
  2. The Bun-compatible work is JSON5, JSONC and finishing Blob.json(); all three need one strict, non-recursive reader that builds ordinary-prototype objects. jread + jbuilder can be that reader once given a strict mode and a prototype option.
  3. JsonPushParser should grow the @streamparser/json surface (onValue, paths, end()), the only widely used shape for it.
  4. Our Json* classes have no standard to follow; they stay as the engines under the standard surface (CLAUDE.md: no new custom public API). JsonWriter and JsonParser remain because lib/jsonStreams.js and JsonSerializer need them.
  5. Keep write(undefined) returning undefined and the JSON.stringify rule set exactly; the differential test is the guard.

#7.1 What this shows

  • No runtime exposes the position of a JSON parse error as a structured, correct value. The only correct ones are npm json5 (lineNumber/columnNumber), jsonc-parser (offset/length/code) and Bun's bundler classes (position).
  • Bun's line/column on SyntaxError look like the answer and are not: they locate the JSON.parse call, as JSC does for every error. Do not copy them; do not alias them.
  • Custom exception classes appear for tools, not for JSON.parse: BuildMessage, ResolveMessage, AggregateError (Bun), TokenizerError/TokenParserError (@streamparser/json), ParseError (@xmldom/xmldom, see the XML document). The platform keeps SyntaxError for parsing.
  • Streaming parsers (@streamparser/json, jsonparse, sax, parse5) report through a callback and keep going; whole-text parsers throw at the first error; jsonc-parser is the only one that collects.
  • Message conventions differ in every runtime; only the class (SyntaxError) is common.

#9. Target: exceptions and locations

The contract all JSON parsers follow (the same text is in api-interface-json.md section 11):

  • parse failure is a SyntaxError with an own, non-enumerable loc: a Location (file, line, column, charOffset, byteOffset) at the start of the offending token (1-based, as JSON.parse tools and json5 count), plus length (characters of the offending span, 0 at end of input) and a stable code string (unexpected-token, unexpected-eof, invalid-escape, invalid-number, unterminated-string, trailing-comma, unexpected-comment, trailing-data, ...);
  • bad argument type is a TypeError, never ReferenceError; InternalError is never used for input problems;
  • a failing Reader or user callback keeps its own exception; ours is not wrapped over it;
  • streaming parsers deliver each error to onError(err) with the same SyntaxError, and recover; collecting parsers throw an AggregateError whose errors are those SyntaxErrors (Bun's Bun.build shape);
  • promise APIs (Blob.json()) reject with the same SyntaxError.
