#Event model: sources, sinks, pull and push; the C modules are engines, the APIs are glue (plan 2026-10-18)

> Status 2026-10-18 (implemented). The event model is in: every class is a source or sink over JsonEvent / XmlEvent, pump()/connect()/tee/JsonBuilder/XmlBuilder exist, parse() and XMLNodeParser are removed (next() and the iterator replace them), xml.write() is xwalk pumped into an XmlWriter (XW_PRETTY, indent 2), quickjs-json.c is 1412 and quickjs-xml.c 1339 lines. > Running state and what is left: event-model-state.md. Text below that describes parse(), XMLNodeParser, > eventName/eventValue, PARSE_*, xtreewrite or xlayout is the plan or the history, those are gone.

Shared design of json and xml. api-interface-json.md and api-interface-xml.md refer here for everything about how parsers, builders, walkers, writers and serializers connect; the step list is TODO.md, "Event model v2". The implemented parts are listed in the status note above.

#1. The decision

#DecisionReason
M1every class of quickjs-json.c / quickjs-xml.c is a source or a sink, and pull or pushone vocabulary for every connection; any source reaches any sink of its family without JS in between
M2a source produces JsonEvent / XmlEvent; a sink consumes them as JsonEventSink / XmlEventSinkexists (jevent.h, xevent.h)
M3the pull parsers write the event they found into a caller's JsonEvent / XmlEvent: json_next(p, &ev), xml_next(p, &ev) (json_parse() / xml_parse() stay as the low-level step)a forwarding loop is 3 lines; the token text, the position and the type travel together
M4the push parsers hand the same JsonEvent / XmlEvent to a handler; a sink is a handler (jevent_send)no second callback shape (jr_callback, xr_callback, jr_str_t, xr_str_t go)
M5the walkers are pull sources of the same events (jwalk_event, xwalk_event)walker plus writer = serializer, walker plus builder = clone, with no WalkInterface adapter per writer
M6the native modules export engines only: parsers, builders, walkers, writers, serializers, sink adaptersJSONL, JSON5, JSONC, read, write, DOMParser, XMLSerializer, XML.parse, Blob.json() ... are not C
M7every dialect and runtime API is a thin composition in JS under lib/ (lib/bun.js, lib/dom.js, lib/jsonStreams.js, ...)the portable surface follows the standards in CLAUDE.md order; the engines stay replaceable
M8a dialect that needs a different tree shape (Bun's XML.parse with '@name', '#text') starts as a JS sink in the gluethin first; a C builder mode only when measured slow

#2. The roles

source (produces events)sink (consumes events)
pull (the client asks)JsonParser, XMLParser, XMLNodeParser (over a Reader); the walkers jwalk, xwalk (over a JS value)the serializer: a writer that runs its source only as far as the client has read bytes
push (the producer calls)JsonPushParser, XMLPushParser: the client feeds chunks, events go to a connected sinkJsonWriter, XMLWriter, JsonBuilder, XmlBuilder (also flat), JS-object sinks, tee, rewriters (a sink that owns a sink)

How they connect. "pump" is the C loop while(next(source, &ev) == EVENT) send(sink, &ev).

from \ topush sink (writer, builder, JS sink, tee, rewriter)pull sink (serializer)
pull sourcepump, one loop, no JS call per eventthe serializer is exactly this pump, stopped when the demand is met
push sourcedirect: the parser holds the sink and calls it while write(chunk) runsnot offered: it would need a queue between the two; feed a push sink and read its buffer

Everything else is composition of these cells:

JsonParser(Reader) ──pull──► pump ──► JsonBuilder              JSON.parse, JSON5.parse, JSONC.parse, JSONL.parse
JsonParser(Reader) ──pull──► pump ──► JsonWriter               reformat, minify, JSON5 to JSON
JsonPushParser ──push──► tee ──► JsonBuilder + JsonWriter      streams, onValue
JwalkIterator(value) ──pull──► pump ──► JsonWriter             JSON.stringify, JSON5.stringify
JwalkIterator(value) ──pull──► Serializer ──► read(n)          JsonStringifyStream, Response body
JsonParser ──pull──► Serializer ──► read(n)                    streaming reformat of a file
XMLParser(flat) ──pull──► pump ──► XmlBuilder(flat)            XMLNodeParser (a flat object list)
XMLParser ──pull──► pump ──► XmlBuilder                        xml.read(), DOMParser tree
xwalk(tree) ──pull──► pump ──► XmlWriter                       xml.write(), XMLSerializer
JS value ──walker──► JS sink (object with methods)             Bun.XML.stringify, custom shapes

#3. The pull contract

#3.1 JSON (include/json/json.h, jevent.h)

typedef enum {
  JSON_PULL_FAIL = -1, /* an exception is pending; only engine-bound sources (walkers) */
  JSON_PULL_END = 0,   /* no more events */
  JSON_PULL_AGAIN = 1, /* the Reader has no data now; call again once it may */
  JSON_PULL_EVENT = 2, /* *ev is filled */
} JsonPull;

JsonPull json_next(JsonParser*, JsonEvent* ev);
JsonPull jwalk_event(JwalkSource*, JsonEvent* ev);   /* JwalkSource = a JwalkIterator + the capture of its last step */
Rule
errors are eventsa malformed span is ev->type == JSON_EVENT_ERROR, str the message, at its start; the parser resyncs, the next call goes on (lenient) or returns JSON_PULL_END (strict dialects stop at the first one)
textstr / len of error, number, string, key, comment point into the parser, valid until the next call
positionat and has_at = 1, always set by the parsers: the start of the token (SourcePos), not the end
commentsJSON_EVENT_COMMENT only with the comments flag, otherwise skipped inside the parser (not by the pump)
status vs eventstatuses are never event types, so the -1 that means JSON_NONE in json_parse() today and XE_ERROR in xml_parse() can no longer be confused
enginenone for the parsers; the walkers hold JSValues and may return JSON_PULL_FAIL (a toJSON that throws, a bigint)
numberingJSON_PULL_END / JSON_PULL_AGAIN equal JSON_PUMP_END / JSON_PUMP_AGAIN, so the pump returns the status that stopped it

#3.2 XML (include/xml/xml.h, xevent.h)

typedef enum { XML_PULL_FAIL = -1, XML_PULL_END = 0, XML_PULL_AGAIN = 1, XML_PULL_EVENT = 2 } XmlPull;

XmlPull xml_next(XMLParser*, XmlEvent* ev);
XmlPull xwalk_event(XwalkSource*, XmlEvent* ev);
Rule
textname / nlen and value / vlen point into the parser's ev_name / ev_value, valid until the next call
one text slotXmlEvent gets anonymous-union aliases str / len for name / nlen: text, comment, declaration, instruction, cdata and error carry their text in str / len as JsonEvent does; XE_ATTRIBUTE is the only event with value (NULL: a bare attribute)
strict errorXE_ERROR event, then XML_PULL_END (a mismatched end tag is terminal); lenient mode never produces it, repairs are reported through onParseError (api-interface-xml.md 11)
typed markupthe parsers produce XE_COMMENT, XE_DECLARATION, XE_INSTRUCTION, XE_CDATA instead of elements with magic names (!--, !, ?); the builder maps them back for read() compatibility
positionat from tag_line / tag_column (the < of the tag, a closing tag's own < for the ends it causes)
modestolerant, flat, no_implied_end, self_closing_tags stay parser options; flat makes XMLNodeParser a plain XMLParser feeding a flat builder

#3.3 The loop

ssize_t
jevent_pump(JsonEventSource src, const JsonEventSink* sink) {
  JsonEvent ev;
  JsonPull st;
  ssize_t r;

  while((st = src.next(src.opaque, &ev)) == JSON_PULL_EVENT)
    if((r = jevent_send(sink, &ev)) < 0)
      return r;
  return st;
}

json_pump() and xml_pump() are this (json_source(), xml_source(), jwalk_source(), xwalk_source() make the JsonEventSource / XmlEventSource). A client that wants to look at the events (skip, count, branch) writes the loop itself, the contract is the same.

#4. The push contract

typedef ssize_t JsonEventHandler(void* user, const JsonEvent*);   /* jevent_send(sink, ev) has this shape, user = sink */

ssize_t jr_feed(jr_state_t*, const char* chunk, size_t len, JsonEventHandler*, void* user);
ssize_t jr_end(jr_state_t*, JsonEventHandler*, void* user);
Rule
handlergets a JsonEvent, the same struct a pull parser fills; has_at set, text valid inside the call
resultthe first negative handler result stops the parse and is returned; 0 otherwise
chunkingunchanged: output is the same at every chunk size, tokens may span chunks
to a sinkjr_feed(st, chunk, n, jevent_handler, &sink); jread_pump / xread_pump shrink to that call and then go
XMLPushParserthe same for XmlEvent; gains tolerant, implied ends, flat and locations by running xml.c over a push Reader (Phase 6 of TODO.md Tier 20), or xread stays a tokenizer feeding the same handler

The JS-callback mode of JsonPushParser / XMLPushParser (onValue, onError, the raw (type, ...) function) is a handler that calls a JS function: the JS-sink adapter of section 6, not a third mechanism.

#5. Walkers, builders, writers, serializers

#Walkers are pull sources

WalkIterator keeps the JS-value stack, skip and the circularity check. jwalk and xwalk gain an internal capturing WalkInterface that stores the event it was just handed, and *_event() turns it into a JsonEvent / XmlEvent:

walkerJS valueevent
jwalkstring, keystr / len as CESU-8 (JS_ToCStringLen2(..., 1)), so jwrite pairs or escapes surrogates; owned by the iterator until the next call
jwalkfinite numberJSON_EVENT_NUMBER, text = the shortest round-trip form (what JSON.stringify writes); NaN, Infinity -> JSON_EVENT_NULL
jwalkJSON.rawJSONJSON_EVENT_NUMBER with the raw text when it is a number, else a raw pass-through (an optional JsonEventSink.raw, see M-Q3)
xwalk{tagName, attributes, children}XE_ELEMENT_START, XE_ATTRIBUTE*, XE_TEXT / nested starts, XE_ELEMENT_END; the interpretation now in xtreewrite.c moves here, xtreewrite becomes a pump into xwrite
xwalkflat list [{tagName}, 'text', {tagName: '/x'}]the same events; {tagName: '/x'} is XE_ELEMENT_END

#Builders are push sinks

JsonBuilder, XmlBuilder (also XB_FLAT) are JsonEventSink / XmlEventSink already. Additions the dialects need:

AdditionFor
proto option: ordinary objectsevery *.parse result (D3 in api-interface-json.md)
a queue of completed roots, each with the SourcePos where it ended; take() returns and clears itJSONL.parse (every document), JSONL.parseChunk (read = end of the last complete root), onValue
builder error policy: an JSON_EVENT_ERROR is recorded, not thrownthe pump decides (3.1); the builder is never the one that throws
jbuild_value_js()Bun.XML object shapes written as a JS sink can still push finished values into a C builder

#Writers are push sinks

JsonWriter and XMLWriter keep their options (indent, bare_keys, single_quotes, hex_numbers, minify; XmlWriteOptions). Their JS methods are the sink methods (objectStart, key, number, elementStart, attribute, ...) from js_jsonsink_define / js_xmlsink_define, so a JS script drives them by hand or the pump drives them in C. JsonWriter.value(v) (a JS value) stays as sugar: a walker pumped into itself.

#Serializers are the pull sink

typedef struct {
  JsonPullSource src;   /* a JsonParser or a JwalkIterator behind one function pointer */
  JsonWriter wr;        /* writes into out */
  DynBuf out;           /* unbounded: one step may write a lot, nothing is replayed */
  size_t pos;           /* bytes already served */
  JsonPull status;
} JsonSerializer;

/* read(n): while out holds fewer than n unserved bytes and status == EVENT, take one event from src, send it to wr. */
Rule
demandread(n) steps the source one event at a time until n bytes are buffered or the source ends; a step is never re-run (its JS side effects, toJSON and getters, run once)
sourcea value (walker made for it) or any pull source: new JsonSerializer(parser) reformats a file as far as it is read
boundaryread(n) may cut a UTF-8 character; the JS class offers read(n) in bytes and readText(n) on character boundaries (BUGS xmlserializer-read-n-splits-utf8)
XMLXMLTreeSerializer is the same struct over XmlEvent; the replay code (skip, delivered, capped) is deleted
streamspull(controller) of a ReadableStream is read(highWaterMark); that is all JsonStringifyStream and a Response body need

#6. The JS surface of the engines

#6.1 Handshake and the connect methods

Each module .so has its own copy of the class ids (static core lib, quickjs-native-bindings skill section 8), so json cannot recognise an xml object by class. Every engine class that can be a source or a sink carries a native method on its prototype that answers for its own class:

Symbolanswered byreturns
Symbol.for('qjs.jsonsink') / Symbol.for('qjs.xmlsink')JsonWriter, JsonBuilder, tee, rewriter, JsonPushParser's inner sink ...the JsonEventSink (an address for the receiving module)
Symbol.for('qjs.jsonsource') / Symbol.for('qjs.xmlsource')JsonParser, XMLParser, XMLNodeParser, walkersthe pull source
MethodOnDoes
source.pump(sink)#pull sourcesruns the loop of 3.3 in C; sink is a handshake object or any object with the sink methods (then wrapped by the JS-sink adapter, one JS call per event); returns END, or AGAIN for a Reader that ran dry; throws the SyntaxError of the first error event unless onError is set (api-interface-json.md 11.1)
pushParser.connect(sink)#push sourcessets the sink that write(chunk) / close() drive; pushParser.sink reads it
new JsonSerializer(source_or_value, options)#pull sinksection 5
tee(a, b, ...)#sinksa sink that sends every event to each; the result is a sink

JsonParser.next() / the iterator protocol stay as the pull-by-hand form and return event objects shaped like JsonEvent ({type, value, loc}), so token ids are the JsonEventType / XmlEventType ones, not private numbers.

#6.2 JS-object sinks (the other direction)

js_jsonsink_wrap / js_xmlsink_wrap (exist) turn a C sink into a JS object. The missing twin, a JS object turned into a C sink (jsonsink_from_js(ctx, obj)): each member calls obj.<method>; used by pump() when the target has no handshake, and by the JS-callback mode of the push parsers. A JS sink may return a negative number or throw: that stops the pump and the exception propagates unchanged (api-interface-json.md 11.1).

#7. The glue in lib/

The glue imports engine classes and nothing from the layer above; each file is the portable surface of one runtime or standard. Every function below is composition of the engines, no parsing code.

FileSurface (standard)Composition

Rules for the glue:

  • No engine class is subclassed to add a standard API: the standard API is a function or class in lib/ that uses one.
  • A dialect is a name passed to the parser ('json', 'jsonc', 'json5', 'jsonl', and the JR_* flags behind them), never a parallel entry point.
  • Error shaping (SyntaxError with loc, length, code; AggregateError; onError) is done once, in the engines' pump() / push-parser code (api-interface-json.md 11); the glue only chooses strict or collecting.
  • A runtime that already has the standard (Bun.JSON5, DOMParser) is not shadowed: the glue installs only what is missing, as lib/bun.js does for Bun.*.

Behaviour worth knowing:

  • A flat list with XWALK_BALANCED ends what a marker for an outer element leaves open ([p, 'hi', br, 'x', /p] gives <p>hi<br>x</br></p>); knowing void elements is the consumer's business.
  • max_depth is counted as xml.write() counts it (two walk levels per element level); a cut element has no end event.
  • json_next() reports at as the start of the token, line and column 1-based; jr_feed() takes it from jr_state_t.tok.

The old entry points (json_parse, xml_parse, jr_read, xr_read, jr_callback) stay until the bindings are off them.

#12. After the bindings are lifted: what lives in include/ and src/

Measured 2026-10-18 by grep of quickjs-json.c (1961 lines) and quickjs-xml.c (2158 lines) against include/ and src/ (src/ and include/ of json 6030, xml 5263, walk 778 lines). Three kinds of change: code moves in from the bindings (engine-bound helpers that are not classes), code becomes private or goes (the old entry points the bindings no longer call), and duplicate engines merge. Order: P11 and P12 first (they make the binding lift small), then the lift itself, then P13 to P16. Every deletion has the same gate: grep shows no user outside its own file, ctest unchanged (the same eight known failures).

#12.1 What moves in

The bindings keep only the classes: constructor, getters, finalizer, argument checks, the JSCFunctionListEntry tables. Everything that converts between JS and events without being a class goes down, so the other module (json / xml) and later bindings can reuse it.

Today a binding reads them from parser internals (err_code 10 sites, err_len 9, tag_line 3); with the fields on the event the parsers' structs can be private (12.2) and push and pull errors look the same. This is P11 and is a header change only.

#12.3 What merges (measure first)

Two duplicate engines exist per format; both directions of the merge are possible, so this is a measurement, not a decision.

PairWhy they existMergeGate
jread.c (push, 1546 lines) and json.c (pull, 1148 lines, deleted 2026-10-18, json_next is now a queue over jread)json.c resumes on JSON_NEED_DATA, so it is a push parser over a chunk Reader that answers "dry"; jread over a pulled chunk plus a queue is a pull parser.
