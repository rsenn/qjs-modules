#XML: our API against Browser, Bun, Node, Deno and JS packages

What xml (quickjs-xml.c, lib/xml.js, lib/html.js, lib/dom.js) offers, set next to what the other runtimes and the widely used packages offer. Priority when they disagree: WHATWG > Browser > Bun > Node > Deno. Companion documents: api-implement-xml.md, api-interface-xml.md, native/xml.md, and the plan in TODO.md Tier 20.

Method: probed on node 22.23.3, bun 1.4.2, deno 2.9.7 and the qjsm of this tree (2026-10-17). Packages were installed and run on one document: fast-xml-parser 5.11.2, sax 1.6.1, saxes 6.0.0, @xmldom/xmldom 0.9.12, htmlparser2 12.0.0 (xmlMode), xml2js 0.6.2, xmlbuilder2 4.0.3, txml 6.0.3. The document is <a x="1"><b>t</b><b>u</b>tail<c/></a>.

Node and Deno have no XML support at all; everything there is a package. In the browser the object model is the DOM, so the browser standard is the DOM subset, not a plain-object tree.

Observations:

  • Our tree is txml's tree (tagName, attributes, children, text as bare strings). It is also the only shape that keeps document order for mixed content, which is why lib/dom.js is built on it. Bun's object form loses the interleaving of text and elements (its own limitation: "#text":"tail" stands for text anywhere).
  • The three object-form libraries (Bun, fast-xml-parser, xml2js) agree on repeated names becoming arrays and differ on how attributes and text are marked (@x/#text, @_x/#text, $/_). Bun's is the standard we follow.
  • Event parsers agree on the same four events; ours delivers ATTRIBUTE as its own event where the others fold attributes into the open event. That is a deliberate fit for the resumable pull design.

#5. Name clashes and gaps against the standards

  • XMLSerializer: in every browser it is new XMLSerializer().serializeToString(node). Ours is a pull serializer new XMLTreeSerializer(tree).read(n) (was XMLSerializer). Same name, different contract, so a browser script importing it from xml breaks silently. Options: rename ours (XMLTreeSerializer), or give it a serializeToString(tree) method so both uses work. Decided: renamed.
  • DOMParser and XMLSerializer in the DOM sense exist in lib/dom.js as Parser and Serializer; exporting them under the DOM names (DOMParser.parseFromString(str, type) returning a Document) is the standards lift with the most users.
  • XML.parse and XML.stringify (Bun) are missing; a converter exists in the attic (attic/), the plan is a mode of the new pieces rather than a second implementation.
  • No XSLT, no XMLHttpRequest; out of scope.
  • Package event APIs (sax family) have no equivalent need: XMLParser and XMLPushParser already cover them.

#6. Findings and what they decide

  1. Keep the tagName/attributes/children tree: it matches txml, is the lossless one and lib/dom.js depends on it.
  2. Add Bun's XML.parse/XML.stringify as a conversion mode over the same parser and walker (priority Bun after Browser; there is no Browser plain-object form).
  3. Export the DOM subset under its standard names from lib/dom.js (priority Browser); resolve the XMLSerializer clash first.
  4. Make XMLWriter escape (the only one of our writers that does not), as every package above does.
  5. A strict mode on src/xml/xml.c closes the Bun gap in section 3 without losing the HTML tolerance.

#7.1 What this shows

  • Two models: the browser's (never throw, put the error in the result) and the library models (throw, callback, or return a {code, line, col} record). Bun, the only runtime with XML parsing, throws SyntaxError without a position.
  • Structured positions exist only in libraries: xmldom (ParseError.locator), fast-xml-parser (line, col, code), parse5 (start/end line, column, offset, code). Their numbering is 1-based, and the three use different names for the same thing.
  • Stable error codes are what clients branch on (fast-xml-parser, parse5, jsonc-parser); message texts are not stable anywhere.
  • A custom exception class is used by a parsing library only to carry the position (ParseError); the platform class for the same job is SyntaxError.

#9. Target: exceptions and locations

Same contract as JSON (the text is in api-interface-xml.md section 11), with these XML specifics:

  • strict failures are SyntaxError with own non-enumerable loc (start of the offending token or tag), length and code (mismatched-end-tag, unexpected-eof-in-tag, duplicate-attribute, unquoted-attribute-value, undefined-entity, multiple-roots, text-outside-root, invalid-character, unterminated-comment, bad-xml-declaration, ...);
  • the lenient (HTML) mode throws nothing and reports what it repaired through an optional onParseError(err) with the same SyntaxError-shaped object (code, loc, length), using the HTML spec's code names where one exists (parse5's callback name and codes);
  • event parsers keep their status protocol (PARSE_ERROR) and gain an error getter holding that same SyntaxError;
  • the DOM subset follows the browser: DOMParser.parseFromString(s, 'text/xml') returns a document with a <parsererror> element and does not throw (lib/dom.js), while xml.read() and XML.parse() throw.
