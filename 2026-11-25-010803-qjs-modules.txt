● I replaced the sed one-liner with a shared script. I haven't run a real build
  with it, only a standalone check of the shim.

  What was wrong with the sed approach
  - The same three lines were pasted into four files.
  - It used sed -i, which isn't portable (BSD and macOS differ).
  - It depended on the layout of config.sub (insert at line 2).
  - It wasn't idempotent: libpq and libsqlite patch a shared SOURCE tree, so
    each SUFFIX build would stack another echo line.
  - It threw away canonicalization for every triplet, including ones config.sub
    already knows.

  The fix
  - New script: cmake/deps/PatchConfigSub.cmake is run as a cmake -P script.
  - Backup: It renames config.sub to config.sub.orig.
  - Shim: It writes a small shim that tries the original first. If the original
    rejects a triplet (dietlibc and the like), the shim echoes the argument back
    unchanged.
  - Re-runs: A second run does nothing, because config.sub.orig already exists.
  - Call sites: All four Build*.cmake files now use one line:
  PATCH_COMMAND ${CMAKE_COMMAND} -DSOURCE_DIR=<SOURCE_DIR> -P
  ${CMAKE_CURRENT_LIST_DIR}/PatchConfigSub.cmake

  Verification
  - On a dummy config.sub, a double run left it patched once, with .orig kept.
  - An unknown triplet passed through unchanged.
  - The dummy config.sub.orig wasn't executable, so the check only exercised the
    fallback path. The shim's "try the original first" path is untested.

  The new script uses file(CHMOD), which needs CMake 3.19 or newer. I didn't
  check the project's minimum version.

● The ONNX Runtime C API (header version 1.32, ORT_API_VERSION 32) is much
  larger than the binding. qjs-ort binds 24 of the OrtApi function-table
  entries, about 6% of the table.

  The C API

  The header is
  qjs-ort/third_party/onnxruntime-linux-x64-1.32.0/include/onnxruntime_c_api.h,
  about 9,400 lines.

  - Dispatch: There are no free functions. Everything goes through const 
    OrtApi*, obtained with OrtGetApiBase()->GetApi(ORT_API_VERSION). OrtApi has
    roughly 385 members.
  - Errors: Nearly every call returns an OrtStatus*. NULL means success.
    Otherwise you read GetErrorMessage and GetErrorCode, then call
    ReleaseStatus.
  - Handles: There are 11 opaque handle types, each with a Release* function.
    The main ones are OrtEnv, OrtSession, OrtSessionOptions, OrtValue,
    OrtMemoryInfo and OrtAllocator.

  The API breaks down into these areas:

  Area: Env and logging
  What it covers: CreateEnv, CreateEnvWithCustomLogger, thread pools, telemetry
  Bound?: CreateEnv only
  ────────────────────────────────────────
  Area: Session options
  What it covers: graph optimization level, intra/inter-op threads, execution
    mode, profiling, memory-pattern, config entries, free dimension overrides,
    initializers, custom op domains
  Bound?: create and release only
  ────────────────────────────────────────
  Area: Execution providers
  What it covers: CUDA, TensorRT, OpenVINO, DML, CoreML, NNAPI, XNNPACK, QNN and

    others, through AppendExecutionProvider*
  Bound?: none
  ────────────────────────────────────────
  Area: Session
  What it covers: CreateSession, CreateSessionFromArray, Run, RunAsync,
    RunWithBinding, input/output counts, names and type info, model metadata,
    profiling
  Bound?: CreateSession, Run, counts and names
  ────────────────────────────────────────
  Area: Values and tensors
  What it covers: CreateTensorWithDataAsOrtValue, CreateTensorAsOrtValue, string

    tensors, sequences, maps, sparse tensors, GetValueType, GetTensorMutableData
  Bound?: float32 tensors over a typed array, plus a few getters
  ────────────────────────────────────────
  Area: Type and shape info
  What it covers: element type, rank, dims, symbolic dims
  Bound?: element type, dims and count
  ────────────────────────────────────────
  Area: Memory and allocators
  What it covers: CreateCpuMemoryInfo, CreateAllocator,
    GetAllocatorWithDefaultOptions, arena config
  Bound?: the CPU memory info and default allocator
  ────────────────────────────────────────
  Area: IoBinding
  What it covers: CreateIoBinding and device-side binding
  Bound?: none
  ────────────────────────────────────────
  Area: Training, custom ops, Model Editor, Compile API
  What it covers: OrtTrainingApi, custom op registration, graph construction
  Bound?: none

  What is bound

  Everything is in quickjs-ort.c (822 lines) plus the helper files js-utils.c
  and js-utils.h.

  API surface exposed to JS
  - Module export: version.
  - Tensor: getters type, dims and data. The constructor new Tensor('float32', 
    Float32Array, dims) takes the typed array without copying.
  - Session: getters inputNames and outputNames, and the methods run(feeds) and
    release().

  Proof of concept status
  - The proof of concept in tests/u2netp-poc.js runs u2netp.onnx. It matches
    OpenCV dnn to 7.6e-5 maximum difference, at about the same speed (290 ms
    against 294 ms).
  - There is also a test with a hand-built Add model.

  C functions used (24):
  - Setup and errors: CreateEnv, CreateSessionOptions, CreateSession, Run,
    GetErrorMessage, GetErrorCode, ReleaseStatus.
  - Session introspection: SessionGetInputCount, SessionGetOutputCount,
    SessionGetInputName, SessionGetOutputName, GetAllocatorWithDefaultOptions.
  - Tensors and shapes: CreateCpuMemoryInfo, CreateTensorWithDataAsOrtValue,
    GetTensorMutableData, GetTensorTypeAndShape, GetTensorElementType,
    GetDimensionsCount, GetDimensions, GetTensorShapeElementCount.
  - Release functions: ReleaseValue, ReleaseSession, ReleaseSessionOptions,
    ReleaseTensorTypeAndShapeInfo.

  What the planned API still lacks

  The remaining items come from qjs-ort/TODO.md, in its order.

  1. Tensor element types: only float32 works. The planned list also includes
     float64, int32, int64, uint8, bool, string and float16.
  2. Session options: the constructor takes only a path today. Still to do:
     - Session(pathOrBuffer, options) with providers, intraOpThreads,
       interOpThreads, graphOptimization and logLevel
     - inputs and outputs with type and shape
     - ort.providers
  3. Build and distribution:
     - fetching ONNX Runtime from CMake
     - aarch64 and Termux builds, where Android needs the aar
     - a cross-build against a sysroot
  4. Later, no C API bound yet:
     - async run through a worker thread
     - extra execution providers (XNNPACK, NNAPI, CUDA)
     - an ort backend in qjs-opencv's opencv-imgproc.js

  Out of reach for now. Nothing is planned for IoBinding, sparse tensors,
  sequences and maps, model metadata, profiling, custom ops, the training API,
  or the Model Editor and Compile APIs.

  The README.md still says "design stage, no code yet". The README is stale,
  since the proof of concept works. The README's "Planned API" table is the
  reference for where the binding is heading.
