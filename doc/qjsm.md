# qjsm — REPL with module functions

Source: `src/qjsm.c` (~2800 lines), built on top of the `quickjs-modules` static
library (`src/*.c`) and every native module this build was configured with
(`quickjs-*.c`).

`qjsm` is this project's own QuickJS shell/REPL binary — a sibling of upstream
QuickJS's `qjs`, built from a private fork of it, that adds everything qjs-modules
exists to provide: a real ES module loader with builtin/`node:`/`data:`/JSON/alias
resolution, a `process`-shaped bootstrap, and a set of `*Module` introspection
functions on `globalThis` for working with the module graph from script code.

## Why qjsm exists (vs. plain `qjs`)

Upstream `qjs` (`quickjs-libc.c`'s `qjs.c`) is deliberately minimal: it exposes
`std`/`os`, a bare-bones `import`, and nothing else. That's the right default for
the reference implementation, but it's not enough to actually *use* qjs-modules:

- qjs-modules ships ~30 native C modules (`fs`, `path`, `child-process`,
  `sockets`, `inspect`, `xml`, `dom`, ...) and ~45 JS modules (`lib/*.js`). Plain
  `qjs` has no way to know these exist, let alone resolve a bare specifier like
  `import fs from 'fs'` to one of them.
- Plain `qjs`'s loader only understands filesystem paths. It has no concept of a
  builtin-module registry, an `QUICKJS_MODULE_PATH` search path, `node:` prefix
  aliasing, `data:` URLs, JSON modules, or `package.json`-driven aliasing —
  every one of those is a qjs-modules-specific addition.
- Plain `qjs` has no `process` global, no `require()`-flavored introspection of
  what's loaded, and its REPL (`qjs -i`) has no notion of importing a module
  interactively.

`qjsm` is the shell that actually dogfoods qjs-modules: every module in the
build is registered into it as a builtin, `lib/process.js` is imported
automatically at startup (so `process`/`console` behave like they do under
Node/Bun/Deno — see the project's [API-compatibility priority](README.md)), and
the module loader is rewritten from scratch (`jsm_module_normalize`/
`jsm_module_loader`) to support the resolution order below. Everything else in
qjs-modules — `fs`, `path`, `stream`, ... — works identically under plain `qjs`
too (that's a deliberate design constraint: no module may *require* `qjsm`); `qjsm`
is specifically the convenience shell for developing and exploring this stack
interactively, not a dependency of it.

| | `qjs` | `qjsm` |
| --- | --- | --- |
| Module loader | Filesystem paths only | Builtin registry, `node:` prefix, `data:` URLs, `.json`, `package.json` `_moduleAliases`, `QUICKJS_MODULE_PATH` search, Node-style `registerHooks()` resolve/load hooks |
| Builtin modules | None | Every native/JS module the build was configured with, statically registered |
| Bootstrap globals | `std`, `os` (only with `--std`) | `process` (always), plus `std`/`os` with `--std`; `console` from the REPL |
| Module introspection | None | `findModule`, `loadModule`, `requireModule`, `normalizeModule`, `resolveModule`, `locateModule`, `registerHooks`, `moduleList`, `moduleEntries` on `globalThis` |
| REPL | Line evaluator only | Line evaluator + `\`-directives, including `\i <module>` to import interactively |
| `-m` flag | N/A | Loads named modules onto `globalThis` before the main script/REPL runs |

## Design ideas

**One loader, layered resolution.** Rather than several competing module
systems, `qjsm` registers a single `JSModuleLoaderFunc`
(`jsm_module_loader`) and normalizer (`jsm_module_normalize`) with the engine
via `JS_SetModuleLoaderFunc()`, and every special case (builtin, `data:`,
`.json`, alias, path search) is a branch inside that one pipeline, tried in a
fixed precedence order (see below). Anything not recognized falls through to
the engine's own default filesystem loader (`js_module_loader()`).

**Builtins are a build-time-generated table, not a runtime registry.**
`jsm_builtin_modules[]` (a `Vector` of `BuiltinModule` records: name, init
function or bytecode blob, cached `JSModuleDef*`) is populated once at startup
by expanding `#include "quickjs-builtins.h"` through the
`jsm_builtin_native(name)`/`jsm_builtin_compiled(name)` macros. That header is
*generated by CMake* (`CMakeLists.txt`, written to
`${CMAKE_CURRENT_BINARY_DIR}/quickjs-builtins.h`) from the set of native
modules the build was configured with (`QUICKJS_MODULES`) and the set of
`lib/*.js` files precompiled to QuickJS bytecode via the `qjs` compiler at
build time (see the root `CLAUDE.md`'s note on `modules/*.c` generation). So
"what's builtin to this `qjsm`" is a compile-time property of the build, not
something assembled by scanning a directory at runtime — a release binary and
a WASM/Emscripten build can ship a different builtin set without any code
change, just a different `QUICKJS_MODULES` list.

A builtin is only actually *initialized* (native module function called, or
bytecode `JS_ReadObject`'d and evaluated) the first time it's imported
(`jsm_builtin_init()`), and the resulting `JSModuleDef*` is cached on its
record — so listing 30 builtins costs nothing if a script only imports 3 of
them.

**A shadow list, because `JSModuleDef` is opaque.** The engine keeps its own
internal list of loaded modules (`ctx->loaded_modules`), but nothing in the
public `quickjs.h` API exposes it or the module's own name back to embedder
code (module *identity* — the `JSModuleDef*` — is public via
`JS_TAG_MODULE`/`JS_ResolveModule()`/`JS_GetModuleNamespace()`, but "what's the
name of this loaded module" and "list everything that's loaded" are not).
`qjsm` keeps its own parallel list, `loaded_modules` (a `struct list_head` of
`LoadedModule { name, module }` records), appended to by `jsm_module_loader()`
every time it resolves a specifier. `moduleList`/`moduleEntries`,
`findModule`, and the loader's own re-entrancy cache
(`jsm_module_find()`) all walk this shadow list rather than reaching into engine
internals — see [Implementation notes](#implementation-notes-and-history) for
why that restraint matters.

**Everything interesting is a `globalThis` function, not a CLI-only
feature.** `-m module` (load a module onto `globalThis` before the main script
runs) and `loadModule('module')` (do the same thing from script code) are
literally the same code path (`jsm_module_load()`) — the CLI flag just queues
its argument into `module_list`, drained once at startup. Likewise the REPL's
`\i module` directive (`lib/repl.js`) is just calling the exported
`loadModule()` *JS* helper there, which itself is a thin wrapper around
`import()` — a separate, simpler thing from the C-level `loadModule` global
described below (same name, same idea, two independent implementations: one
for scripts, one for the REPL). The goal throughout is that nothing requires
dropping into a debugger or recompiling to inspect the module graph — it's all
reachable from a one-liner.

## Module resolution pipeline

`jsm_module_normalize(path, name)` and `jsm_module_loader(name)` run in that
order for every `import`/`import()`. Normalize tries, in order:

1. **Builtin registry** — if `name` has no `.`/`/` (a bare specifier) and
   `jsm_builtin_find(name)` matches a compiled-in module, resolve to it
   directly (no filesystem access at all).
2. **Relative/`./`/`../` import** — joined against the *importing* module's own
   resolved path and normalized (`path_normalize2()`), skipped for a `data:`
   importer (see the comment at `jsm_module_normalize()` for why: naive
   `/`-splitting on a multi-KB `data:` URL body finds a `/` inside the source
   text, not a directory boundary).
3. **Explicit shared-library suffix** (`.so`/`.dll`/...) with no path
   component — searched via `QUICKJS_MODULE_PATH`.
4. **Existing relative file** — resolved to an absolute path directly.

Then, in `jsm_module_loader(name)` once a candidate name is in hand:

1. **`data:` URL** — `jsm_module_data()`: `data:[<mime>][;base64],<payload>`.
   `/javascript`or`/ecmascript` MIME evaluates the payload as a module's
   source (URL-decoded, or base64-decoded if `;base64` is present); `/json`
   MIME wraps it as `export default JSON.parse(...)` instead.
2. **`node:` prefix** — stripped (except `node:os`, which would alias to this
   engine's own `os` builtin, which is *not* Node's `os` — see the comment at
   `jsm_module_loader()`), so `node:path` behaves like bare `path`.
3. **Registered hooks** (`registerHooks()`, see below) — when any are registered,
   steps 1-2 and 4-7 collapse into the hook chain's final `nextLoad()` and a
   `load` hook can answer for any URL (`data:` included). With none registered
   this step is skipped and the steps below run exactly as before.
4. **`package.json` `_moduleAliases`** (`jsm_module_package()`) — a Node
   `module-alias`-style map, read once per process and cached
   (`jsm_load_package()`), keyed by the specifier relative to cwd.
5. **Builtin registry** (again, now that aliasing/hooks may have rewritten the
   name).
6. **`.json` suffix** — `jsm_module_json()` wraps the file's contents as
   `export default <parsed JSON>` and compiles that.
7. **Everything else** — the engine's own default loader
   (`js_module_loader()`), i.e. read-and-compile a file from disk.

Every module that resolves this way (steps 1-7, plus builtins) gets a
`LoadedModule` entry appended to `loaded_modules`, whether or not it's
`import`ed again later — that shadow list is qjsm's only source of truth for
"what's loaded" (see [Design ideas](#design-ideas)).

## Import attributes

`with { type: "json" }` works in static and dynamic imports, and the attributes
reach the loader, so `type` decides how a file is read whatever its name:

```js
import config from "./config.json" with { type: "json" };

const data = await import("./data.dat", { with: { type: "json" } }); // parsed as JSON
```

qjsm checks the **keys**, as the specification and plain `qjs` do: `type` is the
only supported one, and any other (`with { foo: "bar" }`) is a `TypeError` when
the import is resolved, in a static and in a dynamic import. The values are not
checked: `type: "nope"` and a `.json` imported with no attribute at all still
load, which Node, Bun and Deno refuse. For a script that has to run there too,
always write `with { type: "json" }`. The old `assert { ... }` keyword is a
`SyntaxError`.

## Builtin modules

The set of builtins is exactly `QUICKJS_MODULES` (native, e.g. `fs`, `path`,
`sockets`) plus every `lib/*.js` file the build precompiles (e.g. `console`,
`util`, `process`, `assert`) — see `CMakeLists.txt`'s `BUILTIN_HEADER`
generation. Query the live set from script code:

Node's subpath builtins resolve to flat modules: `fs/promises` (and `node:fs/promises`) is
`fsPromises`, `timers/promises` is `timersPromises`. The compiled-in list is the CMake cache
variable `BUILTINS_COMPILED`; an existing build directory keeps its cached value, so pass
`-DBUILTINS_COMPILED=...` (the current default is in `CMakeLists.txt`) when a module is added
to it. A compiled module's own imports of other compiled modules must be listed in its
`<name>_MODULES` set in `CMakeLists.txt`.

```js
console.log(builtins);          // array of registered builtin names
console.log(moduleList);        // [{name, builtin}, ...] for everything actually loaded so far
```

## `*Module` globals

Every one of these is installed via `JS_SetPropertyFunctionList()` in `main()`
(`jsm_global_funcs[]`), dispatched through a single C function
(`jsm_module_func()`) keyed by a `magic` enum — one dispatcher, one place to
reason about the module-identifier argument conventions shared across all of
them. A module is identified by its index in `loaded_modules` (the order of
`moduleList`); these functions never hand out a raw `Module` value. Where a module
is taken as an argument, a loaded-module name is accepted too.

| Global | Description |
| --- | --- |
| `findModule(name, [start])` | Look up an already-loaded module by name, starting at index `start`. Returns its position in `loaded_modules`, or `-1` (not an exception) if nothing matches. Index `0` is valid. |
| `loadModule(path, [name])` | Synthesizes and evaluates `import tmp from 'path'; globalThis[name] = tmp;` (or `import * as tmp`/`tmp()` for the `*`/`!` modifiers — see `jsm_module_script()`). This is what `-m` and the REPL's `\i` ultimately call. |
| `requireModule(name)` | CommonJS-flavored `require()`: loads the module and returns its full namespace object (`JS_GetModuleNamespace()`), rather than binding it onto `globalThis`. |
| `resolveModule(index)` | Runs `JS_ResolveModule()` (link the module's imports/exports) on an already-loaded module. |
| `getModuleName(index)` | The module's name (`JS_GetModuleName()`). |
| `getModuleMetaObject(index)` | The module's `import.meta` object (`JS_GetImportMeta()`). |
| `getModuleNS(index)` | The module's namespace object (`JS_GetModuleNamespace()`). |
| `normalizeModule(pathOrIndex, specifier)` | Exposes `jsm_module_normalize()` directly — what would `specifier` resolve to, importing from `pathOrModule`? |
| `locateModule(name)` | Path-search only (`jsm_module_locate()`): where would `QUICKJS_MODULE_PATH`/extension search find `name`, without importing it? Returns `null` if not found. |
| `registerHooks({resolve?, load?})` | Node's synchronous `module.registerHooks()` — see [Module customization hooks](#module-customization-hooks). Also exported as `registerHooks` from the `module` builtin. |
| `moduleList` *(getter)* | Array of module items, see [Module items](#module-items). |
| `getModule(nameOrIndex)` | The `moduleList` item for a module, or `null` if it isn't loaded. |
| `moduleEntries` *(getter)* | Array of `[name, moduleValue]` pairs, skipping synthetic (`<...>`-named) modules. |
| `builtins` *(getter)* | Module items (see [Module items](#module-items)) for every registered builtin. One not loaded yet has only `name`, `kind` and `builtin`. |
| `evalFile(path, [asModule])` / `evalBuf(source, [filename], [asModule])` | Evaluate a file or in-memory source, optionally as a module (in which case the return value is `{name, exports}` rather than the completion value). |
| `scriptList` / `scriptFile` / `scriptDir` / `__filename` / `__dirname` *(getters)* | Views of the include/import stack (`jsm_stack`) — which file is currently executing and its ancestry. |
| `startInteractive()` | Drops into the REPL from script code, same as `-i`/`SIGUSR1`. |

An earlier `addModule(name)` global (queue a path for the *next* `-m`-style
load) was removed — see
[Implementation notes](#implementation-notes-and-history): the queue it wrote
to is only ever drained once, at startup, before any user script can run, so
calling it from script code was a silent no-op.

### Module items

`moduleList` and `getModule()` return items with these properties; `index` is
the argument the other `*Module` functions take.

| Property | Meaning |
| --- | --- |
| `index` | position in `moduleList` (load order; fixed once the module is loaded) |
| `name` | resolved module name |
| `kind` | `'native'`, `'compiled'`, `'data'`, `'json'` or `'js'` |
| `builtin` | registered in the builtin table |
| `path` | file the module was loaded from (absent for builtins and `data:`) |
| `url`, `main` | the module's `import.meta.url` / `import.meta.main`, when set |
| `parent` | `index` of the module that imported it first (absent for the entry point and eval'd code) |
| `hooked` | `true` when produced by a `registerHooks()` hook; absent otherwise |
| `status`, `async` | `'unlinked'` … `'evaluated'`, and whether it uses top-level await (needs the engine's `JS_GetModuleStatus()`) |

## Module customization hooks

`registerHooks()` follows Node's synchronous
[customization hooks](https://nodejs.org/api/module.html#customization-hooks);
`Bun.plugin()` (`doc/js/bun.md`) is built on the same chain.

```js
import { registerHooks } from 'module';

const hooks = registerHooks({
  resolve(specifier, { parentURL, conditions, importAttributes }, nextResolve) {
    if(specifier === 'virtual:hello') return { url: 'virtual:hello', shortCircuit: true };
    return nextResolve(specifier);
  },
  load(url, { format, conditions, importAttributes }, nextLoad) {
    if(url === 'virtual:hello') return { format: 'module', source: 'export default "hi"', shortCircuit: true };
    return nextLoad(url);
  },
});

hooks.deregister();   // also [Symbol.dispose], for `using`
```

| Rule | Detail |
| --- | --- |
| Order | Last registered runs first; the engine's own resolution/loading is the final `next*()`. |
| Chain | A hook must call `next*()` or return `shortCircuit: true`, else `Error` with `code: 'ERR_LOADER_CHAIN_INCOMPLETE'`. |
| `resolve` returns | `{ url, format?, shortCircuit? }`. `format` is handed on as `context.format` to `load`. |
| `load` returns | `{ format, source, shortCircuit? }`; `source` is a string, `ArrayBuffer` or typed array. |
| Formats | `module`, `json`, `builtin`, `addon` (the last two with `source: null`); `commonjs`, `wasm` and the `*-typescript` formats throw `TypeError`. |
| URLs | Hooks see `file:///abs/path`, `node:fs` (`os` and `std` stay bare), `data:` and any custom scheme; the module key (`loaded_modules`, `import.meta`, relative resolution) stays the plain path/bare name. |
| Errors | An exception thrown by a hook propagates to the `import` (it no longer ends the process). |
| Sync only | A hook returning a Promise throws `TypeError`; the async `module.register()`/`initialize` thread API is not provided. |
| Scope | Per thread (workers start with none); not inherited. |

The old `moduleLoader({normalize, loader})` global was removed; port
`normalize` to `resolve` and `loader` to `load` (see `lib/nodeModulesLoader.js`).

## REPL integration

`qjs -i`/`qjsm -i` (or the `USR1` signal, or `startInteractive()`) enters
`lib/repl.js`'s `REPL`. Its `\`-prefixed directives include:

```
\i module          import a module, bind it to its basename on globalThis
\i *module         import a module, Object.assign() its exports onto globalThis
\i !module         import a module, then call its default export
```

implemented by the REPL's own `loadModule()` export (`lib/repl.js`) — a small
wrapper around plain `import()` plus the `*`/`!` modifier handling from
`jsm_module_script()`'s CLI/`-m` syntax, reimplemented in JS since the REPL
doesn't go through the C `loadModule` global at all. Successfully-imported
module names are remembered across sessions (`this.modules`,
persisted via `modulesSave()`/`modulesLoad()` to a REPL state file) and
re-imported automatically the next time the REPL starts, so a module you `\i`
once stays available in later sessions without repeating the directive.

## Implementation notes and history

`qjsm` used to have a second, more invasive way to inspect modules: an
optional `QUICKJS_INTERNAL` build mode that `sed`-scraped `JSModuleDef`'s
private struct layout out of `quickjs.c` at build time
(`quickjs-internal.c`/`.h`, generated, never checked in) to reach fields like
`m->module_name` directly. It was off by default, and by the time of its
removal (commit `26d776f7`) it could no longer be generated against the
current engine at all, so every `#if QUICKJS_INTERNAL` block in `qjsm.c`/
`utils.c` had long since been dead weight for a default build. It's gone now;
the pieces of it that were still load-bearing were reimplemented on top of
public API instead:

- `module_name()`/`module_nameval()`/`module_namecstr()` (`src/utils.c`) used
  to read `m->module_name` via raw pointer arithmetic
  (`*(JSAtom*)((int*)m + 1)`) as their *default*, non-`QUICKJS_INTERNAL` path —
  a guess at the atom's offset that assumed a struct layout the engine no
  longer has (`JSGCObjectHeader` grew to a full `list_head`, moving
  `module_name` to a different offset), so it read garbage and segfaulted
  `normalizeModule()`. Replaced with the public `JS_GetModuleName()`.
- `jsm_module_load()` (backing `loadModule`/`-m`) used to locate the
  just-imported module by walking the engine's own module list positionally
  (`module_next(module_next(last_module))`, skipping the synthetic wrapper
  script's own module) under `QUICKJS_INTERNAL`, falling back to a
  name-based `jsm_module_find()` otherwise — a fallback that never actually
  matched, since `loaded_modules` records a module under its *resolved* name
  (e.g. an absolute `.so` path) while the fallback searched by the original,
  unresolved specifier (e.g. `"sndobj"`). Fixed by tracking the shadow list's
  size before/after the synthetic import and taking the newly-added head
  entry directly (list insertion order already puts the just-imported
  module there, dependencies first) — no name matching needed.
- `requireModule`'s entire body used to live inside a `QUICKJS_INTERNAL`
  block (calling a `module_exports()` helper that, notably, was *never
  itself defined outside that mode* even historically); removing the block
  left the case empty, so it silently returned the engine's
  "no exception" sentinel value as if it were one. Reimplemented on top of
  `jsm_module_load()` + the public `JS_GetModuleNamespace()`.

The general lesson embedded in the design now: anything `qjsm` needs from a
`JSModuleDef` goes through `quickjs.h`'s public accessors
(`JS_GetModuleName`, `JS_GetModuleNamespace`, `JS_ResolveModule`,
`JS_MKPTR(JS_TAG_MODULE, ...)`/`JS_VALUE_GET_PTR`) or through qjsm's own
`loaded_modules` shadow list — never through a guessed struct offset.

## Command-line options

```
qjsm [options] [file [args]]
-h  --help          list options
-e  --eval EXPR     evaluate EXPR
-i  --interactive   go to interactive mode
-m  --module NAME   load an ES6 module (comma-separated; see loadModule() above)
-I  --include file  include an additional file
    --std           make 'std' and 'os' available to the loaded script
    --no-bignum     disable the bignum extensions (BigFloat, BigDecimal)
    --qjscalc       load the QJSCalc runtime (default if invoked as qjscalc)
-T  --trace         trace memory allocation
-d  --dump          dump the memory usage stats
    --memory-limit n   limit the memory usage to 'n' bytes
    --stack-size n     limit the stack size to 'n' bytes
-q  --quit          just instantiate the interpreter and quit
-l  --list          list modules

  USR1 signal starts interactive mode
```

`-m` and `-I` each accept multiple values (`-m a,b,c`, or repeat the flag);
`-m` entries load in order once the bootstrap (`process` import, `--std`
imports) has run, before `-I` includes, before `-e`, before the REPL. See
[Module resolution pipeline](#module-resolution-pipeline) for what a bare
module name in `-m`/`loadModule()` resolves against.
